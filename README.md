# CHIBA//NET

Анонимная доска сообщений в эстетике терминала: фосфорно-зелёный текст на
почти чёрном, скан-линии, мигающий блочный курсор. Регистрации нет — любой
посетитель вводит ник (или оставляет пустым → `anon`) и пишет в общий лог.

**Стек:** Next.js 16 (App Router, TypeScript) · React 19 · Prisma 6 · SQLite.

---

## Локальный запуск

```bash
npm install
npx prisma migrate dev      # создаст prisma/dev.db и накатит миграции
npm run dev                 # http://localhost:3000
```

Локально используется `DATABASE_URL="file:./dev.db"` из `.env` (путь
резолвится относительно `prisma/schema.prisma`, то есть файл ложится
в `prisma/dev.db`). Скопируйте `.env.example` в `.env`, если его нет.

Прод-режим локально:

```bash
npm run build
npm run start               # прогонит migrate deploy, затем next start
```

## Деплой на Railway

### 1. Создать проект из репозитория

Railway → **New Project** → **Deploy from GitHub repo** → выбрать этот
репозиторий. В корне лежит `Dockerfile` и `railway.json`, поэтому Railway
соберёт образ по Dockerfile без дополнительной настройки.

### 2. Добавить Volume и смонтировать в `/data`

В сервисе: вкладка **Variables/Settings** → **Volumes** → **Add Volume**.
Mount path указать ровно:

```
/data
```

Это критично: SQLite-файл должен лежать на volume, иначе при каждом
передеплое контейнер поднимется с пустой файловой системой и все сообщения
пропадут.

### 3. Задать переменную окружения

В **Variables** добавить:

```
DATABASE_URL = file:/data/board.db
```

Именно абсолютный путь внутрь примонтированного volume. Переменную `PORT`
Railway подставляет сам — `next start` её подхватывает, руками задавать
не нужно.

### 4. Проверить, что прогоняется `prisma migrate deploy`

Это уже прошито в старт-скрипте:

```json
"start": "prisma migrate deploy && next start"
```

`Dockerfile` запускает контейнер через `CMD ["npm", "run", "start"]`, то есть
миграции применяются к базе на volume при каждом старте, до того как
поднимется Next.js. В логах деплоя должно быть видно:

```
Applying migration `20260907191459_init`      # при первом деплое
No pending migrations to apply.               # при последующих
```

### 5. Команды build / start

| Этап  | Команда                                 | Где задано              |
|-------|-----------------------------------------|-------------------------|
| Build | `npm ci` → `npm run build`              | `Dockerfile`            |
| Start | `npm run start`                         | `Dockerfile` / `railway.json` |

`npm run build` = `prisma generate && next build`. Клиент Prisma
генерируется внутри образа, поэтому нативный движок собирается под
целевую платформу.

### 6. Одна реплика

В `railway.json` стоит `"numReplicas": 1`. SQLite не шарится между
инстансами — не увеличивайте это число.

### Проверка после деплоя

1. Открыть URL сервиса, отправить сообщение.
2. Нажать **Redeploy**.
3. Сообщение должно остаться на месте — значит база действительно живёт
   на volume.

## API

### `GET /api/messages`

Возвращает последние 200 сообщений в хронологическом порядке.

| Параметр | Описание                                                        |
|----------|-----------------------------------------------------------------|
| `after`  | Вернуть только сообщения с `id` больше указанного (курсор поллинга) |

```json
{ "messages": [ { "id": 1, "nick": "anon", "body": "...", "createdAt": "2026-09-07T19:23:50.393Z" } ] }
```

### `POST /api/messages`

```json
{ "nick": "molly_m", "body": "текст сообщения" }
```

Правила:

- `body` — обязателен, тримится, до 2000 символов;
- `nick` — необязателен, до 32 символов, пустой → `anon`;
- управляющие символы вырезаются, HTML экранируется **до записи в базу**,
  так что строка в БД инертна для любого потребителя;
- rate limit: не чаще 1 сообщения в 5 секунд с одного IP (in-memory,
  по `x-forwarded-for`).

Ответы: `201` с созданным сообщением, `400` при ошибке валидации,
`429` при флуде, `500` при отказе базы. Текст ошибки приходит в поле
`error` в терминальном стиле (`FLOOD CONTROL :: WAIT 4S`).

```

src/app/api/messages/route.ts GET + POST
src/components/
  AsciiHeader.tsx             ASCII-логотип и строка статуса ноды
  Board.tsx                   клиентский оркестратор: стейт, поллинг, отправка
  MessageFeed.tsx             лог с автопрокруткой вниз
  MessageLine.tsx             [дата] <ник> текст
  ComposeForm.tsx             handle: / msg: / [ TRANSMIT ]
  StatusLine.tsx              RECEIVING PACKETS / CONNECTION LOST
src/lib/
  prisma.ts                   singleton клиента
  messages.ts                 чтение и запись, декодирование в текст
  validate.ts                 правила для nick/body
  sanitize.ts                 escape/unescape HTML, вырезание control-символов
  rate-limit.ts               окно 5 с на IP
  format.ts                   YYYY-MM-DD HH:MM:SS
  constants.ts                лимиты и интервалы
```

## Как работает «живая» лента

Страница рендерится на сервере, поэтому лог виден сразу после перезагрузки.
Дальше клиент раз в 4 секунды делает `GET /api/messages?after=<последний id>`
и дописывает только новое. Вкладка в фоне не опрашивает сервер и догоняет
ленту при возвращении фокуса. При ошибке сети статус переключается на
`!! CONNECTION LOST :: RETRYING`, поллинг продолжается.

## Заметки по решениям

- **Prisma 6, не 7.** В Prisma 7 SQLite требует нативный адаптер
  (`better-sqlite3`) и `prisma.config.ts`; это добавляет компиляцию нативного
  модуля в образ. Prisma 6 несёт собственный движок и `prisma migrate deploy`
  работает без лишних зависимостей.
- **Экранирование на записи, декодирование на чтении.** React и так
  экранирует вывод, но хранить в базе уже инертную строку дешевле, чем
  надеяться на каждого будущего потребителя. При отдаче наружу сущности
  декодируются обратно, так что автор видит ровно свой текст.
- **Время.** Сервер не знает часовой пояс читателя, поэтому SSR рендерит UTC,
  а после гидратации клиент перерисовывает метки в локальном времени —
  форма строки та же, рассинхрона гидратации нет.
